# OBJETIVOS.md — torneo-wako-pukemkwan

## 1. Propósito

Este repositorio contiene la aplicación de puntuación y gestión de torneos de kickboxing WAKO (Point Fighting, Light Contact, Kick Light) usada por la Academia Taekwon-Do ITF Pukem Kwan (Castro, Chiloé; instructor Marcelo Vergara) para operar torneos internos reales desde teléfonos celulares: inscripción de luchadores, generación de llave, marcador en vivo sincronizado entre roles (Mesa, Jefe de Mesa, Juez, Pantalla Pública) y soporte para varios tatamis simultáneos.

El problema concreto que originó el proyecto (documentado en `handoffs/HANDOFF_torneo-wako_2026-08-10.md`) fue que la primera versión funcional dependía de `window.storage`, una API exclusiva del entorno de artifacts de Claude.ai: la app funcionaba dentro de ese chat pero no podía abrirse como archivo suelto (`file://`) ni publicarse en un hosting normal como GitHub Pages. Ese problema ya está resuelto: el código fue migrado a Firebase Realtime Database vía `fetch()` (constante `FIREBASE_URL = 'https://sistema-pukem-kwan-default-rtdb.firebaseio.com'`, línea 307 de `index.html`) y el mismo archivo `index.html` de este repo es lo que se sirve públicamente en GitHub Pages (`https://crisvalver9.github.io/torneo-wako-pukemkwan/`, según `handoffs/HANDOFF_torneo-wako_2026-08-14.md`; esta revisión no hizo una petición HTTP a esa URL para confirmarla por red).

A diferencia de la máquina Windows descrita en los handoffs (rutas `C:\Users\luzug\...`, donde existía un archivo de trabajo `torneo-wako-pukemkwan_2.html` separado de una carpeta de publicación aparte `...\torneo-wako-pukemkwan\index.html`), en este repo —que corre en un Mac (Darwin) y cuyos commits recientes están firmados por "Cristobal Valverde <valverdecristobal91@gmail.com>", verificado con `git log`— **no hay separación entre archivo de trabajo y archivo publicado**: solo existe `index.html` en la raíz, y es simultáneamente el código fuente y lo que GitHub Pages sirve. Cualquier edición directa a este archivo es, en los hechos, una edición al sitio publicado.

Ninguno abre una tarea nueva sin cerrar.

El hilo técnico que el handoff del 14 de agosto dejó explícitamente pendiente de confirmar era el siguiente:

> **Preparar y luego aplicar reglas de seguridad más estrictas en Firebase Realtime Database.** El commit `16c5182` ("Votación de jueces (LC/KL) escribe solo su categoría, no el documento completo — preparación para reglas de Firebase más estrictas") modificó el patrón de escritura del voto de jueces para que escriba solo `/torneo/categories/{id}.json` en vez del documento raíz `/torneo.json`. Según el handoff del 2026-08-14, las reglas de Firebase seguían siendo abiertas (`{read:true, write:true}`) como riesgo aceptado para un torneo interno de bajo riesgo.

**Esta revisión sí verificó de forma independiente, leyendo el código, el estado de la condición técnica que faltaba confirmar — y el resultado es que ya está cumplida:**

- `index.html` contiene exactamente 6 llamadas a `fetch(` en todo el archivo (verificado con `grep -c`). De esas, solo 3 son escrituras (`PUT`/`DELETE`): `putCategory()` escribe `PUT` a `/torneo/categories/{catId}.json` (línea 622), `deleteCategoryRemote()` hace `DELETE` sobre el mismo path (línea 630), y `putPin()` escribe `PUT` a `/torneo/pin.json` (línea 642). Las otras 3 llamadas son lecturas (`GET`), dos de ellas sobre `TORNEO_PATH` (`/torneo.json` completo, líneas 600 y 711) y una sobre una categoría puntual (línea 895). No existe ningún otro mecanismo de escritura de red en el archivo (no hay `XMLHttpRequest`, `sendBeacon` ni librerías HTTP externas).
- 19 sitios del código llaman a `putCategory()` — cubre creación/edición de categoría, inscripción/baja de luchadores, cierre de inscripciones y generación de llave, marcador en vivo, votos de jueces, y cierre de combate. Todos pasan por ese único punto de escritura acotado por categoría.
- El commit `16c5182` (2026-08-19) confirma el cierre del ciclo en el propio diff: eliminó por completo la función `writeTorneo(next)`, que era el único lugar del código que aún hacía `fetch(TORNEO_PATH, {method:'PUT', ...})` (escritura del documento raíz completo), y reescribió `vote()` para que use `putCategory()` en su lugar.

Es decir: **la condición "todo flujo de escritura está acotado por nodo, ninguno reescribe `/torneo.json` completo" ya está cumplida en el código actual**, no es una hipótesis pendiente de auditar. Lo único que esta revisión —igual que la del 14 de agosto— no pudo verificar es el estado real de las *reglas* de Firebase en la consola (`console.firebase.google.com`), porque eso vive fuera del repo y no hay ningún archivo `firebase.json` ni de reglas en este proyecto. El objetivo vigente, entonces, ya no es "confirmar que el código está listo" sino:

**Decidir junto con el usuario si corresponde pasar las reglas de Firebase Realtime Database de abiertas (`{read:true, write:true}`) a reglas restringidas por path (p. ej. limitando escritura a `/torneo/categories/$catId` y `/torneo/pin`), dado que la precondición de código ya está satisfecha.** Esto requiere acceso a la consola de Firebase, que ninguna de las dos últimas revisiones (la del 14 de agosto ni esta) tuvo.

## 3. Alcance

**Incluye (verificado leyendo `index.html`, 1922 líneas / 858 620 bytes ≈ 839 KB):**

- Aplicación de una sola página HTML autocontenida (sin build step, JS vanilla, sin frameworks), con tipografía Barlow y logo/favicon de la academia embebidos como `data:` URIs base64 (`<link rel="icon">`, `<link rel="apple-touch-icon">`, `<link rel="manifest">` con manifest JSON embebido, líneas 11–13).
- Cuatro roles/vistas: Mesa, Jefe de Mesa, Juez, Pantalla Pública (confirmado en el menú de inicio, `goTo('mesa_home')` / `goTo('jefe_selectCategory')` / `goTo('judge_selectCategory')` / `goTo('display_selectCategory')`, líneas ~1301–1307).
- Tres modalidades WAKO: Point Fighting, Light Contact, Kick Light (`MODALIDAD_LABELS`, línea 1159).
- Generación de llave de 16 casillas con siembra estándar (`BRACKET_SEED_ORDER = [0,15,7,8,3,12,4,11,1,14,6,9,2,13,5,10]`, línea 807) y normalización defensiva de arreglos dispersos devueltos por Firebase (`arrayFromMaybeSparse`, línea 360, usada en `normalizeCategory` línea 383).
- Soporte multi-tatami mediante campo de texto libre — `<input class="field" ... placeholder="Tatami 1">` (línea 1428), no numérico ni acotado.
- Sincronización entre dispositivos por *polling* a Firebase cada `POLL_MS = 1200` ms (línea 311), con guarda `writeSeq` (declarada línea 572) contra lecturas tardías que revivan un combate ya cerrado.
- PIN opcional (`configurarPin()`, línea 672) que protege solo: declarar ganador manual, reabrir llave, eliminar categoría, y el rol completo de Jefe de Mesa (según comentario del propio código junto a `putPin()`, línea ~630, consistente con el handoff del 14 de agosto).
- Respaldo descargable en JSON (`descargarRespaldo()`, línea 662) y certificado de resultados imprimible (`renderCertificado()`, línea 1597; `window.print()`, línea 1608; CSS `@media print`, línea 193).
- Publicación como sitio estático en GitHub Pages a partir de este mismo `index.html`.

**No incluye (explícitamente diferido o fuera de alcance, según handoffs y ausencia de código correspondiente):**

- **ITF Taekwon-Do** (Sparring semicontacto, Patrones/Tul, Técnica Especial, Rotura de Tablas): no hay lógica de este deporte en el código — la única mención a "ITF" en todo `index.html` (línea 1317, confirmado excluyendo los bloques base64 de fuentes embebidas, que contienen la subcadena "ITF" por azar) es texto de marca estático ("Taekwon‑Do ITF · Castro, Chiloé"), no una función. El handoff del 14 de agosto lo marca como visión de largo plazo, a retomar después de estabilizar WAKO, empezando por Sparring (estructura de puntos con parada, 4 jueces de esquina, "parecida a lo que ya existe") y dejando Patrones/Técnica Especial/Rotura de Tablas para después por requerir un modelo de juzgamiento distinto (comparación cara a cara con banderas/notas numéricas, no combate punto a punto) y pantallas nuevas.
- Autenticación de usuarios o cuentas: no existe ningún sistema de login; la única barrera es el PIN opcional ya descrito.
- Aislamiento entre torneos o "códigos de sala": todo dispositivo que abre la URL pública lee y escribe el mismo documento Firebase (`/torneo`). El diseño soporta un torneo activo a la vez (con múltiples tatamis y categorías dentro de ese torneo), no múltiples torneos independientes en paralelo.
- Reglas restringidas de Firebase: la precondición de código (escritura acotada por nodo) ya está cumplida y verificada en la sección 2, pero el cambio de reglas en la consola de Firebase en sí no está hecho ni pudo confirmarse en esta revisión.
- Suite de pruebas automatizadas, CI/CD o build tooling: no hay `package.json`, ni carpeta de tests, ni configuración de integración continua en el repo (confirmado listando todos los archivos del árbol de trabajo: solo `index.html`, `.gitignore` y `handoffs/`).
- Hosting alternativo a GitHub Pages: Vercel fue evaluado explícitamente y descartado (handoff 2026-08-14) por no aportar nada a un archivo estático sin build ni backend propio.
- Profundización en un ecosistema estilo Sportdata más allá de lo ya investigado/implementado: verificación de pesaje (`togglePesado()`) y certificado imprimible sí están hechos; el resto —rol de juez central ampliado, integraciones— es exploración conceptual mencionada en el handoff del 14 de agosto, no un compromiso de alcance.

## 6. Supuestos y dependencias declaradas

- **Firebase gratuito, sin monitoreo**: se asume que el plan gratuito de Firebase Realtime Database sigue vigente y dentro de cuota; no hay alertas ni límites configurados en el código ni en el repo.
- **GitHub Pages activado manualmente por el usuario**: el handoff del 14 de agosto es explícito en que el usuario activa/desactiva Pages él mismo y que no hace falta recordárselo ni ofrecerse a hacerlo.
- **La URL de Firebase no es secreta**: al estar embebida en el código fuente público (línea 307), se asume —decisión ya comunicada y aceptada por el usuario según el handoff del 14 de agosto— que cualquiera con la URL puede leer/escribir el documento del torneo mientras las reglas sigan abiertas. El estado real de esas reglas en la consola de Firebase no es verificable desde este repo (ver sección 4).
- **Un solo torneo activo a la vez**: el modelo de datos (`/torneo` como raíz única, sin códigos de sala) asume que no hay necesidad de aislar múltiples torneos concurrentes; el soporte multi-tatami es *dentro* de un mismo torneo, no *entre* torneos distintos.
- **El usuario no es programador**: es estudiante de Ingeniería Civil Industrial (confirmado literalmente en ambos handoffs), por lo que la documentación y las explicaciones de trabajo en este repo se mantienen en español de Chile, con lenguaje directo y sin asumir jerga técnica.
- **Identidad de git**: a diferencia de la máquina Windows original (donde el handoff prohibía `git config --global` y exigía pasar `user.name`/`user.email` por commit), en esta máquina Mac la identidad global YA está configurada (`Cristobal Valverde <valverdecristobal91@gmail.com>`, verificado con `git config --global --list` en esta revisión) — no hace falta reproducir esa restricción aquí.
- **Cambios chicos y probados no requieren confirmación previa de `git push`**: excepción explícita pedida por el usuario para reducir fricción; cambios de arquitectura sí requieren confirmación previa.
- **La lógica de progresión de llave (`leafMatch` línea 505, `nextRoundMatch` línea 520, `buildBracket` línea 524) es frágil y ya causó bugs dos veces** (según el handoff del 14 de agosto: una vez advertida desde el handoff original, y el bug de arreglos dispersos corregido el 14 de agosto): cualquier cambio ahí se asume que necesita las pruebas de la sección 5, punto 3, antes de subirse.
